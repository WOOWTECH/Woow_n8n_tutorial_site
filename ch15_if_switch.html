IF / Switch：條件分支

workflow 不會每次都做同一件事。「金額大於 1,000 才通知經理」「客戶是 VIP 才寄致謝信」「表單有勾同意才存資料」——這種「看資料再決定走哪條路」的能力，n8n 靠兩個節點做到：IF（二選一）跟 Switch（多選一）。這章把兩個節點的差別、設定方式、常見坑一次講清楚，讓你以後看到「有時候要 A、有時候要 B」的需求，腦袋自動浮出解法。

為什麼要學條件分支

到第 14 章為止，你會用 {{ $json.amount }} 把上一個節點的資料塞進下一個節點——不錯，但這只是「原封不動地往下傳」。真實的自動化幾乎每一條都會有「岔路」：

  • 訂單來了：金額 大於 1,000 通知經理，其他丟到日常清單就好。
  • 客戶名單進來：VIP 走「寄致謝信＋建 Slack 頻道」，普通客戶只寄自動回覆。
  • 表單提交：勾了同意條款才存資料庫，沒勾就寄「請重新填」的信。
  • 系統告警：等級 critical 打電話、warning 發 Slack、info 只寫 log。

這些「看資料決定走哪條路」的邏輯就叫條件分支（conditional branching），寫程式的人會用 if / else 或 switch / case；在 n8n 裡，你不寫程式，直接放 IF 節點或 Switch 節點，用視覺化的方式拉線接下游——資料進來、節點判斷、走上面或下面（IF）或走哪一號 output（Switch）。

觀念：IF 跟 Switch 都是 n8n 的 Core 節點（第 7 章講過三大類：Trigger / Action / Core）。它們不呼叫任何外部 API、不吃你的 SaaS 額度，純粹在 workflow 內部做流程控制，執行速度幾乎是零成本。

IF vs Switch：哪個時候用哪個

兩個節點都在做「判斷 → 分路」，選錯不會壞，但用對會讓 canvas 乾淨很多。一句話對照：

特徵IF 節點Switch 節點
幾個 output 固定兩個：true（上）、false（下） 可自訂多個（實務上最多 4 個 rule，Expression 模式無上限）
回答的問題 一個 yes/no（例：「金額 > 1000 嗎？」） 一個資料對應多種可能（例：「tier 是 gold、silver 還是 bronze？」）
心智模型 程式的 if / else 程式的 switch / case；像大樓電梯，按幾樓去幾樓
條件寫法 可加多個條件，用 AND / OR 組合 每個 output 各自寫條件（Rules 模式）或直接用一個 Expression 決定去哪號（Expression 模式）
該怎麼挑 只有「要 / 不要」兩條路走時 三條路以上、或明顯的分類（等級、狀態、來源）
提示：「三種以上分類」不是硬規則。你可以疊三個 IF 節點（第一個判 gold、下面接第二個判 silver…），但這會讓 canvas 變成階梯狀，讀起來很累。同一個欄位的多種可能，一律用 Switch 才漂亮。

動手做：加第一個 IF 節點

我們拿一個具體情境：訂單金額大於 1,000 就往「通知經理」走，否則往「日常紀錄」走。假設你的上游節點（可能是 Webhook、Google Sheets、Airtable）已經把訂單以 { "amount": 1500, "customer": "台北文具行" } 這種 JSON 傳下來。

  1. 在 canvas 上加 IF 節點

    在上游節點右邊的 + 圖示點一下（或空白處按 Tab）叫出節點抽屜 → 搜尋框輸入 if → 點 If（在 Flow 分類底下）。節點會落到 canvas 上，自動連好上游。

  2. 設第一個 Condition

    雙擊 IF 節點打開右邊面板。你會看到一個 Conditions 區塊，預設有一列空的比較。三個欄位由左到右填：

    • Value 1（左值）：點欄位進入 Expression 模式，寫 {{ $json.amount }}——這是從上游拿 amount 欄位。
    • Operator（中間）：先在下拉左邊選型別 Number，右邊再選 is greater than（有些版本寫 larger）。
    • Value 2（右值）：填 1000（純數字，不用引號）。

  3. 看節點右邊多了兩條 output 線

    設好 condition 後，IF 節點右側會分出兩條 output：上面標 true（綠色）、下面標 false（紅色）。這就是你可以拉線的兩條路。

  4. 分別接不同下游節點

    從 true 那個圓點拖一條線出去，接你的「通知經理」節點（例：Slack 傳訊息到 #manager 頻道）。再從 false 拖一條線出去，接「日常紀錄」節點（例：Google Sheets Append Row）。canvas 現在會分岔成兩條路。

  5. 存檔＋按 Execute Workflow 測

    Ctrl+S 存檔。canvas 右上按 Execute Workflow。IF 節點跑完會用綠框標示它走的是哪條 output——你看訂單金額 1500 > 1000，理應走 true，實際看到 Slack 節點也跟著亮起來就對了。

  6. 再測一次「應該走 false」的資料

    把上游 mock 資料改成 amount: 800 再跑一次，這次應該只有 Google Sheets Append 那條亮，Slack 那條沒動。兩條都測過，這個 IF 才算真的驗證完。

IF 節點的四種資料型別 Condition

IF 節點的 Operator 下拉分兩層：左邊先挑資料型別，右邊才會顯示對應的比較運算子。挑對型別很重要——挑錯的話「看起來對，跑起來永遠是 false」，是新手第一名踩雷。

型別常見 OperatorValue 2 要填什麼例子
String（字串） equals / not equals / contains / does not contain / starts with / ends with / matches regex 字串（可含 Expression） Value 1 {{ $json.status }}、Operator equals、Value 2 paid
Number（數字） equals / not equals / is greater than / is less than / is greater than or equal / is less than or equal 純數字（不加引號） Value 1 {{ $json.amount }}、Operator is greater than、Value 2 1000
Boolean（布林） is true / is false / equals / not equals 對 is true / is false 不用填；equals 填 true 或 false Value 1 {{ $json.consent }}、Operator is true
Date & Time（日期） is after / is before / is equal / is between ISO 日期字串或 Expression（例：{{ $now }}） Value 1 {{ $json.createdAt }}、Operator is after、Value 2 2026-01-01

另外還有 Array（陣列，例 contains、length equals）跟 Object（物件），比較少用，這裡先跳過。

注意（第一名踩雷）：資料明明是字串 "1500"，你選了 Number → is greater than → 1000——結果永遠是 false。因為字串 1500 不是數字 1500，n8n 不會幫你自動轉。修法：Value 1 改成 {{ Number($json.amount) }} 強制轉型，或者上游用 Expression / Set 節點先轉好。看到「條件應該對卻走 false」，八成就是這個坑。

多條件組合：AND / OR

一個 IF 節點裡可以放好幾個 condition，然後決定它們的組合方式。面板下面有一個 Combine（或叫 Combinator）下拉，兩個選項：

Combinator意思什麼時候用
AND（且） 所有 condition 都要為 true，整個 IF 才算 true 「金額大 而且 付款狀態是 paid 才通知」
OR（或） 只要有一個 condition 為 true，整個 IF 就算 true 「客戶是 VIP 或 訂單超過 5,000 都要通知經理」

範例：訂單金額大於 1,000 AND 付款狀態是 paid

需求是「不只要金額大，還得真的收到錢才通知經理」。開 IF 節點，加兩個 condition：

  • Condition 1：Value 1 {{ $json.amount }}、Operator Number is greater than、Value 2 1000
  • Condition 2：Value 1 {{ $json.status }}、Operator String equals、Value 2 paid
  • Combine：AND

兩個都滿足才走 true。如果 status 是 pending，即使金額 5,000 也會走 false。

範例：VIP 客戶 OR 高額訂單

需求是「特別關照」——只要滿足其一就走 true：

  • Condition 1：Value 1 {{ $json.tier }}、Operator String equals、Value 2 vip
  • Condition 2：Value 1 {{ $json.amount }}、Operator Number is greater than、Value 2 5000
  • Combine：OR
提示：要「A AND (B OR C)」這種混合邏輯，一個 IF 節點的 Combinator 是全域套用（要嘛全 AND 要嘛全 OR），做不出來。這時候有兩招：(1) 串兩個 IF 節點（第一個判 A，true 那條再接第二個 IF 判 B OR C）；(2) Value 1 改用 Expression 寫一整段 JS 判斷式，例 {{ $json.a && ($json.b || $json.c) }}，Operator 選 Boolean is true。第二招比較優雅，但要會寫一點 JS。

Switch 節點詳解：兩種模式

Switch 節點打開來會先問你 Mode：Rules 還是 Expression。這是 Switch 跟 IF 最大的差別，兩種模式的思維完全不一樣。

Mode 1：Rules（規則模式，最常用）

像很多個 IF 疊起來——每個 Rule 都有自己的 condition（跟 IF 節點一樣的 Operator 系統），滿足哪個 Rule 就走對應那個 output。加 Rule 的方法：面板上按 Add Routing Rule，就多出一個 output（節點右邊會多一個圓點）。

例子：客戶等級分三種，不同下游處理。上游丟下來的 item 是 { "tier": "gold", ... }。設 Switch 節點：

  • Rule 0：Value 1 {{ $json.tier }}、Operator String equals、Value 2 gold → output 0 接「寄致謝信＋通知業務」
  • Rule 1：Value 1 {{ $json.tier }}、Operator String equals、Value 2 silver → output 1 接「寄折扣券」
  • Rule 2：Value 1 {{ $json.tier }}、Operator String equals、Value 2 bronze → output 2 接「寄一般歡迎信」

Rules 之外可以打開 Fallback Output（在 Options 底下），沒對到任何 rule 的 item 會走這條路——很好用，通常接一個「未分類」的 log 或告警節點。

Mode 2：Expression（表達式模式，進階）

直接寫一個 Expression 回傳要走 output 幾號（從 0 開始數）。這比 Rules 模式簡潔，但需要你會用 Expression。

同上例用 Expression 模式：

{{ { "gold": 0, "silver": 1, "bronze": 2 }[$json.tier] }}

意思是「查表：tier 是 gold 走 output 0、silver 走 output 1、bronze 走 output 2」。回傳的數字對應 canvas 右側從上到下第幾條輸出線。Number of Outputs 欄位要先設好（例：3），節點才會有那麼多條線可以接。

觀念：Rules 模式對新手友善，看 canvas 就能猜出邏輯；Expression 模式對進階者省設定時間，尤其分類很多、規則單純（一對一映射）的時候。兩種都能達成一樣的效果，選你順手的即可。

常見實例對照表

把 IF / Switch 常見用法整成一張表，看你的需求對到哪一列，直接抄就好：

情境用哪個節點條件設定下游怎麼接
新表單來 → 有勾同意才存 Sheet，沒勾就寄「請重新填」 IF Value 1 {{ $json.consent }}、Operator Boolean is true true → Google Sheets Append；false → Gmail Send Message
訂單金額分級通知：<1000 助理、1000-5000 組長、>5000 經理 Switch（Rules） Rule 0 amount < 1000、Rule 1 amount is between 1000, 5000、Rule 2 amount > 5000 各接一個 Slack 節點，target 頻道不同
Gmail Trigger 收信 → 依寄件人 domain 分流到不同資料夾 Switch（Rules） Value 1 {{ $json.from.split('@')[1] }}、每個 Rule String equals 一個 domain 各接 Gmail Add Label 或 Move Message
系統告警：等級 critical 打電話、warning 發 Slack、info 只寫 log Switch（Expression） Expression：{{ { critical: 0, warning: 1, info: 2 }[$json.level] }} output 0 → HTTP Request 打電話 API；output 1 → Slack；output 2 → HTTP Request 寫 log
訂單狀態 = paid 且金額 > 1000 才通知經理 IF（多條件 AND） 兩個 condition：status equals paid、amount > 1000；Combine AND true → Slack 通知經理；false → 不接任何節點（沒動作）
Webhook 收 payload → 依 event_type 走不同流程 Switch（Rules） 每個 Rule 一個 event_type 字串 各自接對應的處理節點鏈；記得打開 Fallback 接一個「未知事件」告警
提示：IF 節點的 false output 如果不需要做任何事，可以直接不接任何節點——item 走到那裡就自然停下，不會報錯，也不會影響 true 那條。這是很常見的「什麼都不做」寫法。

IF 後面又接 IF：巢狀分支可以，但要克制

n8n 沒有規定分支不能再分支——IF 的 true 那條下游接一個 Switch，Switch 的某個 output 又接一個 IF，都合法。但視覺上會變成很多岔路，過幾個月你自己回來看都會頭大。

什麼時候可以放心巢狀

  • 兩層以內、每層都很單純（例：先 IF 判 VIP，VIP 那條再 Switch 依國家分區）——canvas 還讀得懂。
  • 下游動作只有兩三步就結束，不是又拉一大串。

什麼時候該抽 Sub-workflow

  • 三層以上的巢狀分支——canvas 變成樹狀圖，肉眼難以追。
  • 同一個判斷邏輯在好幾條 workflow 都出現（例：「這個客戶是不是 VIP」）——抽成 sub-workflow，一改全改，第 19 章會講。
  • 某個分支下游超過 5 個節點——這條分支自成一個小工作流，抽出來單獨測比較好。
注意：巢狀 IF 每一層都會拆一次 items 陣列（走 true 的 items 跟走 false 的 items 各自往下）。如果你上游有很多筆資料，最後每一條分支拿到的 items 數量可能都不一樣，下游節點要小心處理「沒有 item」的情況——這常常導致「上游明明有 100 筆，最後 Slack 只發了 3 則」的困惑。

IF / Switch 常見卡關

條件分支不動、走錯邊、分不出來——把下面對照一次，八成能自己救。

症狀可能原因怎麼救
「兩條分支都走了」 不會發生。IF 是 XOR，每一筆 item 只會走 true 或 false 其中一條。你看到兩邊都亮綠，是因為上游有多筆 items，其中一部分走 true、一部分走 false，兩條下游各拿到自己那份。 點 IF 節點看每條 output 的 items 數，加起來應該等於上游 items 總數
「條件應該對，卻永遠走 false」 資料型別跟 Operator 型別不符（例：資料是字串 "1500"，你選 Number is greater than） Value 1 加轉型：{{ Number($json.amount) }}、{{ String($json.status) }}；或上游用 Set 節點先轉好
「Switch 有些 item 消失了」 那些 item 沒對到任何 Rule，且你沒開 Fallback Output——n8n 就把它們丟掉了 面板 Options → 打開 Fallback Output，多出一條 output，接一個「未分類」節點（例：Slack 通知你、Sheet 記一筆）
「分支之後想合起來，讓下游只寫一遍」 這是正常需求，但需要 Merge 節點 兩條分支的末端拉去接同一個 Merge 節點（第 16 章整章講合流）
「Expression 模式的 Switch 顯示 output 編號無效」 Expression 回傳的數字超出 Number of Outputs 範圍（例設 3 個 output 卻回 5） Expression 用查表或 clamp 保底：{{ ({a:0,b:1,c:2}[$json.type]) ?? 0 }}，找不到走 0
「IF 節點打開沒有 Conditions 區塊，只有一個空白面板」 版本差異或節點沒 load 完 把節點刪了重新加一次；或關掉 canvas 分頁重開 workflow
「用 String contains 沒對到，明明看得到字串裡有」 大小寫敏感（contains 是 case-sensitive）；或欄位前後有空白 Value 1 加 {{ $json.text.toLowerCase().trim() }}，Value 2 也用小寫
「Date is before/after 判斷永遠走 false」 Value 1 拿到的是字串日期，不是 Date 物件；n8n 有時候能自動轉、有時不能 Value 1 改成 {{ DateTime.fromISO($json.createdAt) }} 明確轉成 Luxon DateTime

常見問題

IF 之後我想「兩條都繼續走原本的流程」，怎麼寫？
如果兩條之後要做的事完全一樣，那你根本不需要 IF——直接讓上游接下游就好。IF 存在的目的就是「兩條要做不一樣的事」。如果你的需求是「兩條之後都要做同一件事、只是想加個標籤區分」，正確做法是：不用 IF，改用 Set 節點加一個欄位（例 tag = "vip" 或 "normal"），下游再依這個欄位處理。這樣資料流不分岔，也保留了分類資訊。
一個 workflow 太多 IF 會不會拖慢速度？
幾乎不會。IF / Switch 是純運算，不呼叫外部 API、不做 I/O，一個 IF 執行時間通常是毫秒級甚至更短。真正拖慢 workflow 的是 API 呼叫（Gmail、Sheets、HTTP Request 這些）跟大量 items 的迴圈。放 50 個 IF 都比多打一次 Gmail API 快。所以：需要幾個就放幾個，別為了節點少而硬把邏輯塞進 Code node。
條件太複雜、UI 拉不出來，怎麼辦？
改用 Expression 模式——IF 節點的 Value 1 直接寫一整段 JavaScript 判斷式回傳 true/false，然後 Operator 選 Boolean is true。例子：{{ $json.amount > 1000 && ($json.tier === "vip" || $json.paid) && !$json.blocked }}——這種 A AND (B OR C) AND NOT D 混合邏輯，用 Expression 一行搞定。當然，能寫成清楚可讀的更好；真的很複雜就抽到 Code node 裡處理，回傳 { shouldNotify: true }，IF 再判 {{ $json.shouldNotify }}。
IF 節點跑一次算一個 execution 嗎？會吃我的額度嗎？
「execution」有兩個層級，別搞混：(1) workflow-level execution：一次 Trigger 到底跑完算一次，跟裡面有幾個節點無關，這是 n8n Cloud 版計費的單位。(2) node-level execution：每個節點跑一次算它自己的一次，會出現在 Executions 詳情頁，方便你除錯。IF 節點只算 node-level，不會多花 workflow-level 額度。而且 IF 也完全不呼叫任何 SaaS API（不像 Gmail Send 會用一次 Gmail 配額），所以放再多都不會踩到外部服務的 rate limit。Woow n8n 是 self-host 版，兩種都不計費。
Switch 最多能有幾個 output？IF 能有三個 output 嗎？
Switch 節點 Rules 模式的 UI 通常限制在 4 個 Rule（加上一個 Fallback 就是 5 條 output）；Expression 模式的 Number of Outputs 可以設更大（實務上 10 個以上就該考慮抽 sub-workflow 了）。IF 節點永遠只有 2 個 output（true / false），這是設計上的定義——想要三條路就直接用 Switch，不要用「IF 接 IF」硬湊，會很亂。
可以在 IF / Switch 之後再合流嗎？
可以，但要用 Merge 節點（第 16 章整章講）。直接把兩條分支拉去接同一個下游節點，n8n 會把兩條的 items 合併塞給下游——但要小心：合起來的順序不保證、欄位可能不一致。用 Merge 節點的 Append 或 Combine 模式明確控制怎麼合，比較保險。
Switch 的 Rules 從上到下順序有影響嗎？
有——當一筆 item 同時滿足多個 Rule 時（例：Rule 0 是「amount > 100」、Rule 1 是「amount > 1000」，一筆 amount=5000 兩個都符合），n8n 會走第一個對到的 Rule（依 UI 上從上到下的順序）。所以寫多個 Rule 時，把「最嚴格」的條件放上面、「最寬鬆」的放下面，才不會被寬鬆的那條先撈走。或者把每個 Rule 寫成互斥的（例：amount is between 100, 999 / amount is between 1000, 4999 / amount >= 5000），根本不會撞到，順序也就無所謂。
IF 節點的條件可以取上上一個節點的資料嗎？
可以。用 {{ $node['節點名稱'].json.欄位 }}——這是 第 14 章教過的跨節點取值語法。例：{{ $node['Webhook'].json.body.customer_id }}。條件裡跨節點取值很常見（例：現在的節點是「查詢客戶」的結果，但你想用「Webhook 觸發時的原始 payload」做判斷）。注意節點名稱區分大小寫、中間有空白要保留。
可以動態決定分支數量嗎（例：依上游資料才知道要幾條）？
不能。canvas 上的 output 數量是設計時寫死的，不會執行時才長出來。如果你的分類是動態的（例：「有幾種 tier 我事先不知道」），正確做法是：用 Split In Batches 或 Item Lists 把資料按 tier 分組，然後對每一組跑同一段下游邏輯（可能塞進 Sub-workflow）——這比動態長 output 有彈性得多，也比較符合資料處理的思維。
