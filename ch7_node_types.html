第 7 章

三種節點：Trigger / Action / Core

前面六章你已經會登入 n8n、認得工作區、還會把別人做好的 workflow 抄過來改。從這章開始要動手拉自己的了——但在動手前，你得先看得懂節點抽屜。幾百個節點、十幾個分類看起來很嚇人，其實從功能角度只有三大類：開頭的（Trigger）、做事的（Action）、控制流程的（Core）。這章讀完你看任何 workflow 都是「哦這是 A 接 B 加點 C」。

為什麼要先分類

你到第 3 章看過的節點抽屜——按 Canvas 空白處的 +、或右邊面板點 Add first step，那個從右邊滑出來的清單。裡面東西多到嚇人：

  • 官方節點 400+ 個（Slack、Gmail、Notion、Airtable、HubSpot、Stripe、GitHub…）
  • Core 節點 30+ 個（IF、Switch、Merge、Set、Code、Wait、Function…）
  • Trigger 節點另外還有一大排（Schedule、Webhook、每家 SaaS 都自帶一個 Trigger 版）
  • 再加上 AI／LangChain 系列一整包（AI Agent、Chat Model、Memory、Vector Store…）

你不用背這幾百個名字。真正需要的是——看到一個節點，兩秒內知道它屬於哪一類、能幹嘛。這樣看別人的 workflow 才不會霧煞煞，自己拉的時候才知道該去哪一區找。

提示：這章是純觀念章，沒有動手步驟。看完直接進第 8 章拉你的第一條 workflow，就會自然而然用到這三類節點的分工。

先講結論，一句話對照——

  • Trigger = workflow 的「開頭」，決定什麼時候會跑
  • Action = workflow 的「做事」，跟外部服務（Slack、Sheet、Notion…）互動
  • Core = workflow 的「控制」，管資料流向、條件分支、等待、迴圈

下面三節分別細講。

Trigger 節點：workflow 的開頭

每一條 workflow 都需要一個起點。這個起點就叫 Trigger 節點——它決定「這條 workflow 什麼時候會跑」。你打開節點抽屜第一個看到的分類通常就是 On app event / On a schedule / When called by another workflow 這幾組，全部都是 Trigger。

Trigger 節點有一個很好認的視覺特徵：它左邊沒有輸入圓點。因為它是起點，前面沒東西可接。右邊有一個輸出圓點，把資料往下游送。

Trigger 節點什麼時候會跑典型用途
Manual Trigger 你按下 Execute Workflow 才跑 測試、開發、給人手動點的 workflow
Schedule Trigger 像 Cron，指定時間跑（每小時、每天 8:00、每週一…） 每日報告、每週彙整、每月結算
Webhook 外部系統打 URL 就跑 表單填完、Line Bot、HA 觸發、第三方 callback
App Event（Gmail Trigger、Slack Trigger…） 指定 SaaS 有事情發生就跑 收到 VIP 信件轉發、Slack 提到某關鍵字通知
Chat Trigger 使用者在 chat 介面打字就跑 AI Agent（ch21）做客服機器人時用
Execute Workflow Trigger 另一個 workflow 呼叫你就跑 被抽出來重用的 sub-workflow（ch19）
觀念：一個 workflow 可以有多個 Trigger。例如同一條「新客戶通知」既掛 Webhook（表單填完）、又掛 Schedule Trigger（每天 8:00 補跑一次）、還掛 Manual Trigger（測試時手動跑）——任何一個觸發都會讓整條 workflow 動起來。第 10 章會專門講三大類觸發時機的比較。

Trigger 節點的抽屜位置也很好認——n8n 進節點抽屜的第一頁預設就是 Triggers，你在 Canvas 空白處按 + 開始新 workflow 的時候，n8n 會直接引導你選 Trigger（因為沒 Trigger 就沒起點、workflow 根本跑不起來）。

Action 節點：workflow 的做事的

三類節點裡數量最多的就是 Action 節點——官方 400+ 個節點裡有超過 90% 都是這類。它們的共通點是：每一個節點對應一家外部服務（SaaS、資料庫、雲端），節點內部封裝好那家 API 的所有操作。

如果你用過 Zapier，這個概念一模一樣——Zapier 每個 App 對應一個節點；n8n 也是一家 SaaS 對應一個節點。差別在 Zapier 叫「Actions」，n8n 就叫「節點」而已。

一個 Action 節點裡面通常有很多 sub-operation（子操作）。以 Slack 為例——

  • Send Message：傳訊息到指定頻道或人
  • Update Message：改一則已經傳出去的訊息
  • Delete Message：刪一則訊息
  • Get Channel：抓某個頻道的資訊
  • Invite User：邀某人進頻道
  • …還有 20 幾個其他操作

你不用一開始就記所有子操作。拉出 Slack 節點後，右邊 Operation 下拉選單會列所有選項，你要哪個選哪個。

Action 節點官方大概分成這幾大類，抽屜裡都能對號入座：

分類常見節點典型場景
Communication 通訊 Slack、Discord、Telegram、Email、Line 通知、群發、聊天機器人
Data & Storage 資料儲存 Google Sheets、Airtable、Notion、Postgres、Redis、MongoDB 寫入表格、查資料庫、做資料流
Productivity 生產力 Google Calendar、Todoist、Trello、Asana、ClickUp 建行程、開任務、追進度
Marketing 行銷 HubSpot、Mailchimp、SendGrid、ActiveCampaign 加 lead、寄電子報、追客戶動態
AI 人工智慧 OpenAI、Anthropic、Google Gemini（獨立節點） 生成文案、摘要、翻譯（跟 AI Agent 不同層）
Developer 開發者 GitHub、GitLab、Jira、Bitbucket、Docker Hub 開 issue、建 PR、跑 CI 通知
Files & Cloud 檔案雲端 Google Drive、Dropbox、OneDrive、AWS S3 上傳附件、備份、跨雲搬檔
提示：你完全不需要記這張表。用不到就跳過，需要時再去抽屜搜尋。90% 的人常用的就那五六家（Slack、Gmail、Google Sheet、Notion、HubSpot、GitHub）。

Action 節點的視覺特徵：左右兩邊都有圓點（左邊收上游的資料、右邊送下游），節點圖示通常就是那家 SaaS 的官方 logo（Slack 是紫色井字、Gmail 是紅色信封、Notion 是黑白翻頁）。看到 logo 你大概就知道這是哪家的節點了。

Core 節點：workflow 的控制中樞

三類節點裡數量最少（大概 30 幾個），但也最容易被忽略、同時最重要的就是 Core 節點。它們不跟外部服務講話，職責是管 workflow 內部的資料流跟控制流——像水管的三通、閥門、開關。

Core 節點都放在節點抽屜的 Core Nodes 分類底下（有些版本叫 Flow 或 Data Transformation）。你早晚會用到，特別是當你想寫「如果客戶總金額 > 10000 才通知業務」這種帶條件的自動化。

Core 節點做什麼哪一章細講
IF 條件分支（true 走一條路、false 走另一條） 第 15 章
Switch 多分支（依欄位值走不同路） 第 15 章
Merge 把多路資料合成一路（append / combine / choose） ch16
Split In Batches 把一大批 item 分批處理，避免打爆 API rate limit ch16
Item Lists 陣列操作（去重、排序、聚合、拆開） ch16
Set / Edit Fields 加欄位、改欄位名、重排、扁平化 第 18 章
Code / Function 寫幾行 JavaScript 或 Python 補現成節點不夠的洞 ch20
Wait 暫停一段時間（等 5 秒、等到明天 9:00、等 Webhook） ch17
Execute Workflow 呼叫另一條 workflow（sub-workflow） ch19
HTTP Request 打任何 REST API（沒有官方節點時的萬用鑰匙） 第 12 章
注意：HTTP Request 節點嚴格講其實橫跨 Action 跟 Core——它不綁特定 SaaS（所以放 Core 分類），但功能上是「打外部 API」（所以行為像 Action）。你只要記得：找不到某家 SaaS 的專屬節點 → 用 HTTP Request 自己打 就好。

Core 節點的視覺特徵：左右兩邊都有圓點（IF、Switch 因為要分支，右邊會有多個輸出圓點），節點圖示是抽象幾何——IF 是分岔箭頭、Merge 是箭頭合流、Set 是筆或欄位圖、Code 是尖括號 </>。看不到 SaaS logo 的節點，八成就是 Core。

怎麼看一個節點是哪類

認完三大類，實戰時最有用的技巧是看一眼就能分類。用這三個特徵對照，一秒判斷——

  1. 看左邊有沒有輸入圓點

    左邊沒有圓點（只有右邊出線）→ 一定是 Trigger。這是最直觀的線索。你在 Canvas 上看到一個節點孤零零掛在最左邊，前面沒接東西，那就是 Trigger。

  2. 看名字有沒有 "Trigger" 或 "On ..." 字樣

    節點抽屜裡叫 Slack Trigger、Gmail Trigger、Schedule Trigger、Webhook、On form submission 的都是 Trigger。跟同樣 SaaS 的 Action 節點（例：Slack vs Slack Trigger）擺在抽屜裡通常是不同項目。

  3. 看圖示是 SaaS logo 還是抽象幾何

    圖示是某家 SaaS 的 logo（Slack 紫井字、Gmail 紅信封、Notion 黑白頁）→ 幾乎一定是 Action。圖示是抽象幾何（分岔、合流、齒輪、尖括號）→ 幾乎一定是 Core。

  4. 看抽屜分類

    n8n 抽屜本來就已經分好類了：Triggers 一區、Actions in apps 依 SaaS 分類、Core Nodes 或 Flow / Data Transformation 一區。分不清就回抽屜看它被放在哪個標籤下。

觀念：同一家 SaaS 通常會有兩個節點——一個 Action 版（Slack：主動去 Slack 傳訊息）、一個 Trigger 版（Slack Trigger：被動聽 Slack 事件）。名字很像但職責相反，別選錯。

一個 workflow 通常的節奏

三大類節點在真實 workflow 裡怎麼組合？從最短到最複雜，大概三種節奏：

  1. 最短：Trigger → 1 個 Action

    「每天早上 8:00 傳一則固定訊息到 Slack」——Schedule Trigger 接 Slack (Send Message)，完。兩個節點、一條線，這是最簡單的 workflow 形狀。適合當提醒、當 reminder 用。

  2. 常見：Trigger → 讀資料 Action → Core 過濾 → 寫資料 Action → 通知 Action

    「每天早上抓客服 ticket、只留 urgent 的、寫進 Notion、通知業務主管」——Schedule Trigger → HTTP Request（讀 ticket API） → IF（priority == urgent） → Notion（新增頁） → Slack（通知）。這是最典型的 5 節點 workflow，公司 8 成的自動化都長這樣。

  3. 複雜：多 Trigger → IF 分支 → 平行 Action → Merge → Sub-workflow → 錯誤處理

    「新客戶進來（Webhook + Manual + Schedule 三個 Trigger）→ 依國家分流 → 並行寄歡迎信/加 CRM/開 Slack 頻道 → 合流回主線 → 呼叫『發通知』sub-workflow → 錯了自動 retry 3 次還不行就通知 IT」。這種 15+ 節點的複雜 workflow 你到後面幾章才會慢慢碰到，不用怕。

看得出來，Trigger 通常 1 個（有時多個）、Action 是主力（占節點數 60% 以上）、Core 節點是把 Action 串起來的水管接頭（IF 決定往哪走、Set 整型資料、Merge 合流）。

提示：你以後看到別人分享的 workflow 截圖，可以用這三種節奏對號入座：只有兩三塊就是「最短」、五到八塊是「常見」、十幾塊帶分岔就是「複雜」。看得懂結構才看得懂 workflow 在幹嘛。

抽屜怎麼找節點最快

知道分類是為了看得懂，但實戰時找節點你根本不會一個個滑分類。直接打關鍵字比什麼都快。

  1. 打服務名字：Slack、Sheet、Gmail、Notion

    抽屜最上面有搜尋框，輸入 slack 就會濾出 Slack 相關的節點（Slack、Slack Trigger 都會出現）。99% 的常用整合這樣就找得到。

  2. 打功能字眼：if、set、code、wait、http

    Core 節點沒有 SaaS 名字，用功能字搜。輸入 if 會出現 IF、Switch；輸入 set 會出現 Set / Edit Fields；輸入 http 出現 HTTP Request。

  3. 找不到 → 可能是社群節點（community package）

    比較小眾的服務（例如某台灣本土 SaaS）可能官方沒做節點，但 n8n 有 community nodes（社群套件）機制——需要管理員在後台裝。這個屬於進階操作，找 IT 部門幫忙裝就好。

  4. 完全沒有這家 SaaS 的節點 → 用 HTTP Request 自己打

    官方跟社群都沒有？沒問題，只要那家 SaaS 有 REST API，用 HTTP Request 節點（第 12 章）照 API 文件填 URL、method、header、body 就能打。這是 n8n 的萬用鑰匙——只要對方有 API，你就打得到。

常見狀況排除

剛開始接觸節點抽屜，最常遇到這幾個狀況：

  1. 節點抽屜打不開

    兩種方式：Canvas 空白處按 +、或是新 workflow 就按右邊面板的 Add first step。已經有節點的話，把游標移到某個節點右邊的圓點上會出現 +，點下去也會開抽屜（自動接在該節點後面）。

  2. 抽屜太多分類找不到

    不要一頁一頁滑，直接在最上面的搜尋框打關鍵字。分類是為了瀏覽的人設計的，實戰用搜尋最快。

  3. 我要的節點打了搜不到

    三種可能：（1）拼字對不上——例如你打 google sheets 找不到，試 sheets；（2）可能是社群節點，需要管理員在後台裝 community package；（3）該服務沒官方節點——那就改用 HTTP Request（第 12 章）對它 API 打。

  4. 節點名字改了找不到（Function → Code）

    n8n 定期會改節點名字（例如 Function 節點在 v1 之後改叫 Code；Set 在 v1 之後也叫 Edit Fields）。舊教學裡的名字搜不到就打新名字（Code、Edit Fields）；新版名字通常放在同一個分類下面。

  5. 選了 SaaS Action 節點但左邊沒有輸入圓點

    你可能選成 SaaS 的 Trigger 版了（例如 Slack Trigger 而不是 Slack）。刪掉重選純 Action 版本——搜尋 slack 時同時會出現兩個節點，選沒有 "Trigger" 字樣那個。

  6. 拉了 Core 節點但不知道要接哪

    Core 節點通常放在 workflow 中間（Trigger 跟最終 Action 之間）。IF 放在你要分岔的位置、Set 放在你要整型資料的地方、Merge 放在多路合流處。單獨拉一個 Core 節點沒用，它必須夾在別的節點中間才有意義。

常見問題

n8n 的節點總共有幾種？

n8n 官方支援 400+ 個節點（n8n.io/integrations 的清單）；加上社群套件（community nodes）還有幾百個。實務上 8 成的自動化用不到 20 個節點，別被數字嚇到。

最常用的到底哪幾個？

Woow 內部觀察下來，這 8 個節點涵蓋 80% 的 workflow：

  • Schedule Trigger（Trigger）——定時跑
  • Webhook（Trigger）——外部打進來
  • Slack（Action）——通知
  • Gmail（Action）——寄信
  • Google Sheets（Action）——記錄
  • HTTP Request（Core/Action）——打其他 API
  • IF（Core）——條件分支
  • Set / Edit Fields（Core）——整型資料

把這 8 個玩熟就可以在公司獨當一面了。

AI Agent 節點算哪一類？

算特殊的一類——n8n 把 AI 系列（LangChain family）獨立成一個分類 Advanced AI，跟三大類平行。裡面有 AI Agent、Chat Model、Memory、Tool、Vector Store 等，會組合起來用。第 21 章會專門講。這章你先記得「AI 節點是特殊分類、不歸在三大類裡」就好。

新版節點會不會取代舊的？

n8n 有時候會發新版節點（例：Google Sheets 有 v1、v2；Set 節點在 v1 之後改叫 Edit Fields）。舊版一般會保留讓現有 workflow 不會壞掉；新拉的建議用新版（功能更完整、bug fix 較新）。抽屜裡搜 sheets 會同時出現舊版跟新版，選最新的那個。

Trigger 節點跟 Action 節點差在哪？

Trigger 是被動聽（時間到了、Webhook 進來、SaaS 有事件發生），會自動啟動 workflow；Action 是主動做（傳訊息、寫表格、開帳號），需要上游先送資料才會執行。視覺上 Trigger 左邊沒圓點、Action 兩邊都有圓點。同一家 SaaS 通常都會提供 Trigger 版跟 Action 版兩個節點——Slack Trigger 聽 Slack 事件、Slack 主動打 Slack。

Core 節點會不會跟 SaaS 講話？

不會，這是 Core 跟 Action 最大的差別。Core 節點都只在 workflow 內部處理資料流、控制流——IF 判斷、Set 整型、Merge 合流、Wait 暫停——沒有一個 Core 節點會打外部 API。唯一的例外是 HTTP Request，它雖然放在 Core 分類但功能上是打外部 API，算是灰色地帶。

官方文件在哪查節點細節？

兩個地方：（1）整合節點看 n8n.io/integrations，每家 SaaS 有獨立頁面列所有 operation 跟參數；（2）Core 節點看 docs.n8n.io/integrations/builtin/core-nodes/，官方文件講每個 Core 節點的細節跟範例。

下一步做什麼？

去第 8 章從零拉第一條 workflow：Schedule Trigger（每天 8:00）→ Google Calendar（抓今日行事曆）→ Slack（傳訊息）。剛好就是 Trigger + 2 個 Action 的最短節奏，把這章講的三大類實際感受一次。
